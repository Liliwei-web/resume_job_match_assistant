### 2.4 导出规则（实测；2026-10-08 语义已变更，最新实测见 3.12）

```
GET  /api/resumes/{id}/export   （从未保存过修改稿）  -> 先把工作稿存成 v1 再导出，draft_dirty=False
PUT  /api/resumes/{id}/draft    {"content_md":"PERSIST-MARKER-12345"}
                                                     -> {"draft_dirty":true}
GET  /api/resumes/{id}/export                        -> 新建一版（note="导出前自动保存"）后导出该内容，draft_dirty=False
GET  /api/resumes/{id}/export   （内容没再变）        -> 复用最近版本，不新增版本记录
```

即：工作稿与最近保存版本不一致时，导出会**先自动保存再导出**，所以 `draft_dirty` 恒为 `false`——下载到的就是你屏幕上看到的最新修改稿。只有修改稿为空时才返回 409。

> **这条规则在 2026-10-08 改过**：旧语义是"导出只取最近保存稿，有未保存改动就返回 `draft_dirty: true`、由页面弹窗提示导出的是保存稿"。验收时发现这会让用户以为"导出的是最新版"却拿到旧内容，因此改成先存后导。上面原记录里的 `HTTP 409` 与 `draft_dirty: true` 属于旧语义，已作废。

POST /api/suggestions/2/decision {"decision":"忽略"} -> 200

### 3.5 表达优化建议（polish）：口语化句子拿不到改写的问题与修复

**现象**：简历里“数据库表是我和同学一起建的，后面改过几次”“帮忙看了一下接口慢的问题”这类句子，分析结果里经常没有对应的改写建议，采纳后修改稿和原稿几乎没有区别。

**定位**（同一输入分别看接口结果、模型原始输出，再对原始输出单独跑一遍接地校验）：

```
5 轮同一输入的建议条数： [2, 2, 0, 2, 2]        <- 约 20% 的运行一条建议都不给
5 轮里从未被覆盖的简历行：
   - 帮忙看了一下接口慢的问题，做了一些调整      <- 5/5 完全没被碰过
接地校验对比：模型给出的 2 条建议全部原样保留     <- 不是接地层丢弃的
```

两个原因，都不是“模型没写”：

1. **结构性缺陷**：改写建议只能挂在“岗位要求”条目上（`items[].suggestion`）。《帮忙看了一下接口慢的问题》这句话不对应任何一条岗位要求，因此**永远**进不了建议列表。
2. **输出波动**：`temperature=0.2` 时，同一输入约 20% 的运行一条建议都不给。

**修复**：

- 模型输出增加与岗位无关的 `polish` 数组，专门存放“不对应任何岗位要求、但表达口语化或含糊”的句子；它与岗位条目建议**共用同一套校验**（逐字接地、数字闸门、实体闸门、`action` 规则），并按 `original_passage` 去重。
- 模型温度从 `0.2` 调整为 `0`。
- 提示词明确：`需要补充确认` 的条目也可以给措辞建议，只要改写不依赖尚未确认的信息。

**修复后实测**（同样的输入，5 轮）：

```
第 1〜5 轮：items=6 建议=3（岗位条目建议 2 条 + 表达优化建议 1 条）
被覆盖的句子：
  5/5  '- 用 Python 和 FastAPI 弄了个设备借还的接口'
  5/5  '- 数据库表是我和同学一起建的，后面改过几次'
  5/5  '- 帮忙看了一下接口慢的问题，做了一些调整'
未被覆盖的行只剩教育背景日期与技能列表（本来没有措辞问题）
```

走完整接口流程复验：3 条建议入库、可逐条采纳、重复采纳不重复插入、忽略不改正文、保存后导出与保存稿一致；采纳后修改稿出现实质变化，而原稿保持不变。

**说明**：`polish` 里的建议同样不新增事实——第三条的实际改写是 `- 帮忙看了一下接口慢的问题，做了一些调整` → `- 协助排查接口性能问题，并进行了相应调整`，没有引入任何新的技术栈或数字。

### 3.7 尚未实测与已知波动（如实标注）

- **真实超时/重试路径**：`LLM_TIMEOUT_SECONDS`、`LLM_MAX_RETRIES` 的重试与失败提示是用打桩模拟的（`tests/test_flow.py::test_failed_run_keeps_inputs_and_can_be_retried`），没有真的把 DeepSeek 请求打成超时或断网。

- **第三态的颗粒度依赖**：如第 3.2 节所述，简历里的定性描述是否被判为「需要补充确认」，取决于岗位要求本身是否要求“说明效果／规模”。岗位写得宽泛时，模型可能直接判为「已体现」。

#### 3.8.1 改完和原文一字不差（空建议）

#### 3.8.2 同义换词与空泛补字

实测：`- 负责线上问题的排查与修复，接口响应速度有所提升` → `…得到提升`；`- 参与订单数据表结构调整，配合排查慢查询` → `…慢查询问题`；`- 参与前后端接口联调，配合排查线上页面问题` → `…协助排查线上页面问题`。三条都“有 diff”，但没有带来任何新信息。

**修复**：纳入 3.8.1 的闸门（等价弱表达组扩到“有所／得到／有了”“进行／开展／做了／作出”“配合／协助／协同”），同时提示词写明“定性结果句没有量化数据时不要做同义改写，交给 confirmation_question 去问指标”。复跑后这三条都不再出现。

#### 3.8.3 同一句改写被重复建议

实测（王强 × 初级）：5 条建议里有两组完全重复——岗位要求 1 和 4 都指向同一句简历原文，各自产出了一条一模一样的建议（“表达优化建议”那一路的去重挡不住这种情况）。

### 3.13 改写边界收紧：口语化不自动改写、弱动词只提问、粒度为整段（已执行，2026-10-08，真实模型复验）

**为什么收紧**：第 3.5 节那版“口语化 → 书面化”的换词改写，虽然逐字接地校验能过，但它离“改写事实”只有一步之遥（把“参与”写成“负责”、把“帮忙看了一下”写成“主导排查”都能逃过数字与实体校验）。用户要求把边界改死，于是本轮把口径收敛为三条硬约束：

1. **修改粒度是整段**：`original_passage` 必须是同一小节下连续的 1〜3 行的**完整内容**，不跨段落、不跨小节、不截半句，更不能把相邻段落合并重写。后端是**原地整段替换**（`draft.content_md = content.replace(original, suggested, 1)`），粒度越大越容易越界。
2. **责任边界：参与不等于独立负责**：`original_passage` 里出现“参与／协助／配合／帮忙／跟着／跟随”这类看不出本人产出的词，一律**不给改写建议**，只在 `confirmation_question` 里问清本人做了什么、负责哪一部分、产出是什么；绝不允许替用户把角色升格为“负责／主导／独立负责”。
3. **本轮暂不开放口语化表述的自动改写**：口语词、非专业动词不换词，只在追问里提示“这句话偏口语，建议改成更专业的书面表述（例如把‘弄了’改成‘实现’），请你按真实情况自行改写”——**提示里可以给方向与示例词，但改写结果不得写进 `suggested_passage`**。

同时把“允许做的改动”明确收敛为三类：**结构**（拆长句／合碎片／调语序／加连接词／删冗余）、**语气语态**（被动→主动／去削弱词／主观→客观）、**Markdown 排版**（`- ` 列表化／`**加粗**`／`## ###`／`---`；禁用 `1. 2. 3.` 有序列表，会被后端的数字闸门当成新增量化指标）。few-shot 里原来的两处**换词范例**（“编写→实现”“一起完成→协作完成”）已删除——示例不能和新规则打架；新的范例示范的是**拆句 + 列表化 + 加粗**（`rewrite_reason` 里写明“一个词都没换”）。`polish` 数组保留在协议里，但按新口径正常情况应为空数组。

**自动化**：`backend/tests/test_prompt.py` 新增 5 条断言（本轮暂不开放口语化改写、弱动词角色边界、粒度为整段、允许 Markdown 排版但禁有序列表、few-shot 不含换词范例），后端 **82 passed**。

### 4.1 第一轮发现的既有缺陷：改写建议的「撤销」不会还原文本（第二轮已修复）

**现象**（真实接口实测）：

```
POST /api/suggestions/20/decision {"decision":"采纳"}     -> 200，draft 630 -> 628（改写真落进去了）
POST /api/suggestions/20/decision {"decision":"未处理"}   -> 200，draft 仍是 628（文本没有退回）
GET  /api/analyses/15                                     -> 该建议 decision 已是「未处理」
POST /api/suggestions/20/decision {"decision":"采纳"}     -> 409 原段落未在当前修改稿中找到（可能已被手动编辑）
```

同一份材料、同一条建议，换成「忽略」则能逐字还原（浏览器实测 `630 -> 628 -> 630`）。也就是说：**点「撤销」等于把这条建议卡在“状态说未处理、正文还是改写后文本”的不一致状态里，之后再也采纳不了。**

**根因**：`backend/app/services/analysis.py` 的 `apply_decision` 写的是

```python
elif decision == DECISION_IGNORED and suggestion.decision == DECISION_ACCEPTED:
```

只覆盖「忽略」；而 `backend/app/services/supplements.py` 里同类逻辑写的是

```python
elif supplement.decision == DECISION_ACCEPTED:
```

两个方向（忽略、未处理）都能还原。两处实现不一致，属漏写而不是有意设计——README 第 5 节原先也写着「改为忽略/未处理时会尝试还原」。

第一轮**没有改这行逻辑**（当时任务范围是界面视觉优化 + 保留现有功能，改后端判定语义属于功能变更，需要先确认）。已记入 `README.md` 第 10 节。

**修复（第二轮，2026-10-08，已实测）**：把条件改成“上一次确实采纳过就还原”，与 `supplements.py` 对齐：

```python
elif suggestion.decision == DECISION_ACCEPTED:
```

并补了回归用例 `backend/tests/test_flow.py::test_reset_to_pending_restores_the_body_so_it_can_be_accepted_again`（采纳 → 未处理 → 逐字还原 → 再采纳）。**先把该用例跑在修复前的代码上确认它会失败**（`1 failed`），再确认修复后通过——确保这条用例真的能拦住这个回归，而不是只跟着绿。用例总数 75 → 77（另一条见 4.5）。

修复后真实接口复验（`demo1` / 建议 28 / 修改稿 630 字）：
