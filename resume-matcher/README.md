# 简历与岗位匹配助手（resume-matcher）

面向求职者的 Web 应用：粘贴自己的简历文字与目标岗位描述，系统调用真实模型给出**有依据**的匹配分析与**逐条**修改建议，用户自己决定采纳哪些建议，最终得到可继续编辑、可导出的 Markdown 简历。

> 关键约束：分析结论必须能对应到岗位要求与简历原文；简历里没写的内容只能标为“未体现/需要补充确认”，**不会替用户编造经历、技能、年限或业绩**。

## 1. 技术栈与目录结构

```
resume-matcher/
├── frontend/         React + Vite + TypeScript（构建后由 nginx 托管，并反代 /api）
├── backend/          FastAPI + SQLAlchemy + Alembic（真实后端接口与数据访问）
├── docker-compose.yml   db(PostgreSQL) + backend + frontend 三个服务
├── .env.example      不含真实密钥的环境变量示例
├── README.md
└── docs/             架构说明、测试结果、题目附件与对照表
```

## 2. 快速开始（Docker）

前置条件：已安装 Docker（含 Compose 插件）。**不需要**在宿主机安装 Node.js、Python 或 PostgreSQL。

```bash
cd resume-matcher
cp .env.example .env          # Windows: copy .env.example .env
# 打开 .env，填写 LLM_API_KEY（见第 3 节），其余可保持默认
docker compose up --build -d
```

启动后访问：<http://localhost:8080>（如 8080 被占用，在 `.env` 中改 `APP_PORT`）。

- 首次启动会自动完成：等待数据库就绪 → 执行 Alembic 迁移建表 → 灌入测试账号与预置素材。
- 查看状态：`docker compose ps`；查看日志：`docker compose logs -f backend`。
- 健康检查：`curl http://localhost:8080/api/health`，返回 `llm_configured` 表示模型密钥是否已配置。

如果不想让容器自动灌入示例素材，把 `.env` 里的 `SEED_DEMO_DATA` 改为 `false`。手动初始化命令：

```bash
docker compose exec backend python -m app.seed
```

## 3. 模型配置说明

分析使用 **DeepSeek**（OpenAI 兼容接口），密钥只通过**服务端环境变量**注入，不会出现在前端代码或仓库里。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `LLM_BASE_URL` | `https://api.deepseek.com` | OpenAI 兼容的接口地址 |
| `LLM_MODEL` | `deepseek-chat` | 使用的模型 |
| `LLM_API_KEY` | 空 | **必填**，仅写在 `.env`（已被 `.gitignore` 忽略） |
| `LLM_TIMEOUT_SECONDS` | `90` | 单次请求超时 |
| `LLM_MAX_RETRIES` | `2` | 失败自动重试次数 |

未配置密钥时：接口 `/api/health` 返回 `llm_configured: false`；发起分析会**明确失败**并在页面上显示“尚未配置模型密钥……”，不会用固定结果假装调用成功（符合题目“固定结果不能代替调用”的要求）。

素材设计要点：

- 三份简历都**没有任何量化结果**（“优化了页面加载性能”“接口响应速度有所提升”后面不跟任何数字），用来验证系统不会自行补出“提升 30%”这类指标。
- 缺口技能在简历里**完全不出现**（连“了解”都没有），所以“未体现”是真的没有线索，而不是模型推断“候选人不会”。
- 每份简历都刻意留了 1〜2 句口语化／含糊的表达（“帮运营改过页面配置”“帮忙排查了一些线上报错”“和前端同学一起对接口”）。**这些句子按当前边界只产出追问、不产出改写建议**（口语化表述本轮不自动改写，见第 10 节「已知限制」）；真正会被改写的是**结构、语气语态与 Markdown 排版**，例如把“负责 A，参与 B”拆成两条列表项、给技术栈关键词加粗。反过来，改完和原文一样的“空建议”由 `app/services/grounding.py` 直接丢弃，不会出现在结果里。
- 陈曦简历里补了一句 Vite 的使用场景（“负责前端工程化配置维护，使用 Vite 完成构建与打包”），这样「熟悉前端工程化工具 Vite/Webpack」才能测到**已体现**，同时把“求职意向”从“后端开发工程师”改成“前端开发工程师”（原先与简历标题冲突）。这两处都是**改测试素材**，不是系统代写；如果简历里没有工具名，系统只会判“需要补充确认”。
- 「高级前端工程师」的第 1、2 条**故意拆成两条**（“精通 React、TypeScript”与“有大型前端项目经验”）：合成一条时，模型只能按最弱的那半句判定，整条会掉进“需要补充确认”，一条“已体现”都跑不出来。这是实测结论，见 `docs/test-results.md` 第 3.3 节。
- 「数据工程师」岗位保留作为另一组高缺口样本，可搭配任意简历使用。

## 5. 数据模型与关键取舍

三类内容严格区分，互不覆盖：

| 概念 | 存储 | 特性 |
| --- | --- | --- |
| 原稿 | `resumes.original_text` | 对**系统与模型**只读（分析、采纳、补充都不写它）；用户本人可以在「编辑」里覆盖自己的素材，覆盖走显式二次确认，且不动版本与历史快照 |
| 分析快照 | `analysis_tasks.resume_snapshot / job_snapshot` | 每次分析时冻结当时的简历与岗位 |
| 修改稿 | `resume_drafts.content_md`（工作稿）+ `revisions`（显式保存的版本） | 采纳建议只改工作稿；点击“保存修改稿”生成新版本 |
| 补充记录 | `item_supplements` | 用户为「未体现 / 需要补充确认」条目补写的真实经历：用户原文、模型润色稿、处理状态、实际插入的片段 |

其它取舍：

- **先接地再采信**：模型返回的每条引文都必须能在快照中逐字找到（`app/services/grounding.py`）。找不到的“岗位要求”整条丢弃；找不到的“证据”清空并把状态降级为“需要补充确认”；找不到的“原段落”不生成改写建议。这样事实边界在**分析阶段**就守住，而不是拖到导出阶段再过滤。
- **改写建议要过“数字 + 实体”闸门**：只查数字挡不住“用 Kubernetes 部署”这类编造，所以改写文本还要逐词检查——英文词元（技术栈、工具）、中文技术词、机构／系统名（`…平台/系统/公司/大学`）、中文数量词，只要简历原文里没有，就**不生成建议**，改为补充问题并在理由里列出命中的词。判断“补充”还是“改写”看 `suggestion.action`：`action="补充"` 时 `suggested_passage` 必须为空，带文本会被强制降级为提问。
- **口语化改写由代码兜底，不靠模型自觉**：`app/llm.py` 的 `SYSTEM_PROMPT` 里写了「本轮暂不开放：口语化表述一律不自动改写」，但那只是“请模型配合”——第 4.10 节实测的 4 次运行里有 3 次越界（把“弄了个”改成“实现”）。所以 `app/services/grounding.py` 里补了 `_COLLOQUIAL_MARKERS` 词表与 `find_colloquial_marker()`：原段落命中口语词（`弄了个 / 搞了 / 看了一下 / 帮忙 / 顺手 / 改过几次` 等）时，改写结果不写进 `suggested_passage`，该条降级为提问，理由里写明“请你按真实情况自行改写”。与 `action="补充"` 的处理方式一致，是跟数字、实体闸门同一层的代码级兜底，同样配了回归用例。
- **空建议不进结果**：改写结果和原文一字不差、只增删“了／的”这类助词、只加“问题／情况”这类空泛名词、或只把“有所提升”换成“得到提升”这种同义替换，都会被判定为“没有实质改动”并**直接丢弃**（不是降级成提问，因为原文本身没有信息缺口）。同一句原文被多条要求命中时，只保留第一条上的建议，避免同一句改写重复出现。
- **建议分两路产出**：一路挂在岗位要求上（`items[].suggestion`），另一路是与岗位**无关**的“表达优化建议”（模型输出的 `polish` 数组）。后者是为**不对应任何岗位要求、但本身有结构或排版问题**的句子准备的（例如“帮忙看了一下接口慢的问题，做了一些调整”这类句子，如果只按岗位要求组织建议就永远拿不到改写机会，实测 5/5 轮完全没被覆盖）。按当前边界，口语化改写不开放：原文命中口语词表的条目，模型给出的改写会被代码**降级成提问**并清空 `suggested_passage`，而这一路上被降级的条目**直接丢弃**（提问必须挂在某条岗位要求上才有地方显示），所以这一路正常情况会返回空数组；两路共用同一套接地 + 数字 + 实体校验，并按原段落去重。
- **采纳幂等**：建议有 `未处理/采纳/忽略` 三个状态，重复采纳不会重复插入；若正文已被手动编辑到对不上，返回 409 并提示手动处理。
- **「撤销」与「忽略」都逐字还原正文**：`services/analysis.py` 的 `apply_decision` 只在“上一次确实采纳过”时才执行还原，所以点「忽略」和点「撤销（回到未处理）」都会把改写后的文本按字面换回原段落，不会出现“状态回退了、正文却还是改写稿”。2026-10-08 曾实测到这个漏洞（原实现把条件写死成 `decision == DECISION_IGNORED`，而界面「撤销」送的是「未处理」），修复后补了回归用例 `tests/test_flow.py::test_reset_to_pending_restores_the_body_so_it_can_be_accepted_again`（采纳 → 撤销 → 逐字还原 → 再采纳），并已确认该用例在修复前会失败。
- **补充流程同样由代码守事实边界**：`未体现` / `需要补充确认` 的条目可以让用户补写真实经历，模型只做“口语 → 书面”的措辞优化。此时校验的事实基准换成**用户这一次的输入**（`supplement_violations`）：模型只要多写一个用户没说过的技术栈、公司名或数字，就会被拦下并把命中的词回喂重试，两轮仍越界则返回 422、**不落库也不动修改稿**。采纳只把润色稿插进**修改稿**（原稿不动），并记下“实际插入的那一段”，所以重复采纳不会重复插入、撤销能逐字还原。
- **导出前先自动保存**：`GET /api/resumes/{id}/export` 若发现工作稿与最近一次保存的版本不一致，会先自动存出一版（版本备注写「导出前自动保存」）再导出，响应里的 `draft_dirty` 因此恒为 `false`。这样“导出的就是屏幕上看到的最新修改稿”，不会出现“导出的是旧版本”或“必须先手动保存才能导出”的困惑；代价是导出这个动作本身会写库、多出一个版本记录。
- **删除的两种语义**：删除简历走**级联删除**（改动稿、所有版本、分析任务、建议、补充记录一并通过外键 `ON DELETE CASCADE` 清掉）；删除岗位**不删分析**，`analysis_tasks.job_id` 置空（`ON DELETE SET NULL`），历史分析继续可读，岗位名走分析时冻结的快照。删除前弹二次确认，弹窗里的计数来自 `deletion-preview` 接口；删除语句本身带上 `user_id`，越权时一行都匹配不到。导出按钮（「先导出再删」）只出现在删简历的弹窗里。
- **素材可以改，但历史不会跟着改**：岗位描述与简历原稿都能在卡片上直接改（岗位卡片是「编辑 / 删除」，简历卡片是「预览 / 编辑 / 打开并分析 / 删除」）。改简历原稿是**覆盖**动作，所以要点两次：正文真的变了才出现「确认覆盖并保存」（只改名称直接存，`originalChanged` 用 `.trim()` 比较）。覆盖只写 `resumes.original_text`——`revisions` 一个版本都不动、已冻结的分析快照不动、`job_title_snapshot` 也不变；弹窗里另有一个**默认不勾**的「同时把修改稿重置为新原稿」。这里有个必须写明的陷阱：**新建分析读的是「修改稿优先」（`draft.content_md or original_text`）**，所以只改了原稿却留着旧修改稿时，下一次分析用的仍然是旧修改稿——要么在弹窗里勾上重置，要么在工作台里把修改稿也改过来。
- **权限在后端**：所有查询都按 `user_id` 过滤，越权一律返回 404（不泄露资源是否存在）。
- **分析任务异步有状态**：`pending → running → succeeded/failed`，前端轮询展示；服务重启时会把遗留的 `running` 任务标记为失败，避免永久卡住。

## 6. 关键场景验证步骤与实际结果

### 场景一：明显缺口不会被编造（RES-02 / RES-03）
1. 用 `demo1` 登录，打开「陈曦-前端工程师简历」，选择岗位「后端开发工程师（Go）」，点击“新建分析任务”。
2. Go/Gin、MySQL/SQL、Redis、Docker/Kubernetes、微服务/gRPC 这些要求应显示 **未体现**，“简历对应原文”为空，并给出具体追问。
3. “参与系统性能优化与线上问题排查”这类要求应显示 **需要补充确认**（前端页面的性能优化不能当作后端系统优化），不会把前端线索硬套成后端证据。
4. 技能栏中不会自动出现 Go、Docker 等词；未确认的信息不会自动写进修改稿。

**实际结果**：见 `docs/test-results.md`（场景一）。

### 场景二：对口组合三态齐全（RES-01）
1. 打开「刘洋-Go后端简历」，选择「后端开发工程师（Go）」并分析：Go/Gin、MySQL、Redis 等 **已体现**（证据逐字来自简历）；Docker/Kubernetes、微服务/gRPC **未体现**；“有线上性能调优经验，能够说明优化前后的效果对比” **需要补充确认**（简历只有定性描述，没有前后对比）。
2. 打开「陈曦-前端工程师简历」，选择「高级前端工程师」并分析：React/TypeScript 与 Vite **已体现**（证据逐字来自简历）；“有大型前端项目经验”“熟悉前端性能优化，能给出量化指标” **需要补充确认**；Node.js **未体现**。
3. 重点看那条量化指标要求：简历只写了“优化了页面加载性能”，系统应追问指标而**不自动补出数字**。
4. 再把同一份前端简历换成「后端开发工程师（Go）」岗位跑一次：结果变成整片未体现/待确认——同一份简历换岗位后判断明显反转，说明输出随输入变化，不是固定结果。

**实际结果**：见 `docs/test-results.md`（场景二、场景三）。

### 场景三：采纳 / 忽略 / 重复采纳（RES-04 / VER-01〜VER-03）
1. 打开「刘洋-Go后端简历」，选择「后端开发工程师（Go）」并分析（工作经历里有“负责 A，参与 B”这类可拆句的段落，会触发结构／排版类改写建议）。
2. 对一条改写建议点“采纳”，修改稿内容更新、原稿不变；对另一条点“忽略”，正文不变。
3. 再次点同一条“采纳”，正文不会重复插入。

**实际结果**：见 `docs/test-results.md`（场景三）。

### 场景四：保存、重登与导出（RES-06 / VER-04〜VER-06）
1. 在修改稿里点击“保存修改稿（生成新版本）”。
2. 退出登录并重新登录，修改稿仍是最后一次保存的内容。
3. 点击“导出 Markdown”：如果工作稿还有未保存的改动，系统会先自动存出一版（版本备注显示「导出前自动保存」）再导出，下载内容与**当前修改稿**逐段一致，**不含**分析说明、被忽略建议或未确认问题。

**实际结果**：见 `docs/test-results.md`（场景三、`docs/example-export.md`）。

### 场景五：账号隔离（RES-07）
1. 用 `demo1` 创建/分析简历，退出。
2. 用 `demo2` 直接访问 `demo1` 的简历 id（页面 URL 或接口），应得到 404，无法查看、修改、导出。

**实际结果**：见 `docs/test-results.md`（场景四）。

### 场景六：容器重建后数据仍在（RES-09 / Docker 要求）

**实际结果**：见 `docs/test-results.md`（场景五）。

### 场景七：为「未体现 / 需要补充确认」补充真实经历（RES-01 的延伸）
1. 打开任一分析结果，在 `未体现` / `需要补充确认` 的行卡右上角点“补充”，或在第 4 节**右栏修改稿**的预览里，把鼠标移到对应行上点浮现的“＋”。
2. 弹窗里填写你真实做过的事（例如“我在学校的项目里用 Docker 部署过后端服务，自己写过 Dockerfile”），点“提交给 AI 润色”。
3. 弹窗切到对比视图：左边是你写的原话，右边是模型润色后的书面表达。**模型只能改措辞，不能新增你没写过的技术栈／公司／项目／数字**——如果它写了，接口会直接报错并告诉你命中了哪些词，不会静默放行。
4. 点“采纳”后：该条目变成 **已补充**，修改稿对应位置出现新内容，**原稿依然一字未改**；再点一次“采纳”不会重复插入；把状态改回“未处理”可撤销，修改稿会逐字还原。

**实际结果**：见 `docs/test-results.md`（第 3.9 节，含两段原文/润色稿逐字对照与幂等、撤销实测）。

### 场景八：原稿悬停「编辑」与修改稿悬停「补充 / 删除」（RES-03 / RES-04 的便捷入口）
1. 打开一份已有分析的简历，看第 4 节：**原始简历在左栏（下沉底色 + 只读标记）**，默认是纯文本；鼠标移到某一行上，该行右上角才会浮出一个小图标（铅笔），移开约 200ms 后淡出。原稿栏**没有删除入口**——原稿是只读的，要删段落请到右栏修改稿。
2. 点 **编辑**（铅笔）：
   - 该行对应「未体现 / 需要补充确认」→ 直接弹出补充框，不用先去上面找；
   - 该行对应「已体现」且有改写建议 → 页面滚到上方第 3 节那条建议并高亮闪烁；
   - 只对应条目、没有可跳转的建议 → 滚到上方第 2 节该条目所在行并高亮。
3. 右栏修改稿上悬停才有 **删除**（垃圾桶）：把**修改稿**里的对应行去掉，原稿一字不动；随后出现「已从修改稿删除这一段 · 撤销删除」，点它即可还原。
4. 右栏**修改稿**（「预览」视图）上同样有「＋ 补充」与「删除」两个小图标，效果一致；点「编辑」可切到纯文本框直接改。
5. 预览不够看清时，点右栏标题旁的 **「⤢ 放大」**：弹出宽弹窗，用 16px 字号、更松的行距逐行渲染修改稿，按 Esc 或点「关闭（Esc）」退出。这是**只读**视图，里面不出现补充/删除按钮（避免在大视图里误操作），也更适合逐段核对长文本。
6. 边界：章节标题、过短的行不给删；同一句话在修改稿里出现多次时不给删（避免删错）；如果这一行在修改稿里已被采纳的改写替换掉了，会先把那条建议退回「未处理」再删（此时若本机修改稿有未保存改动，会先提示暂存，避免覆盖）。

**实际结果**：定位与删除规则的纯逻辑见 `docs/test-results.md` 第 3.11 节（跑的是编译后的真实模块）；悬停、淡出与高亮的视觉表现请在浏览器里复核。

### 场景九：删除简历与岗位（计数、级联与越权）
1. 在「我的简历」与「我的目标岗位」卡片上点「删除」，先弹二次确认，弹窗里的计数来自 `deletion-preview` 接口。
2. 删简历：提示「此操作不可恢复，已采纳 N 条建议的修改稿将一并删除」（N = 该简历**历史所有分析**里采纳过的建议总数），底部两个按钮——[先导出再删]（次要）与 [确认删除]（红色危险）。
3. 点「先导出再删」：先按最新修改稿导出 Markdown，导出成功后再执行删除；点「确认删除」则直接删。
4. 删岗位：弹窗**只有提示文字 + [确认删除]**，没有导出按钮（因为不删分析，没有必须先留档的东西）；删除后历史分析仍能正常打开，岗位名一列继续显示当时的岗位名快照。
5. 越权：用 `demo2` 的会话去删 `demo1` 的简历／岗位 id → 404，且 `demo1` 的数据原样还在。
6. 边界：该简历还有**正在执行（running）**分析任务时，删除返回 409 并提示等任务结束再删；只是「创建了但还没跑」的任务（pending）不再阻挡删除——它不写任何数据，后台任务找不到记录会直接返回。

**实际结果**：见 `docs/test-results.md` 第 3.12 节（真实接口 + 真实模型分析实测）。

### 场景十：管理分析记录（查看回放 / 单条删除 / 批量删除）

1. 打开「历史记录」：表格默认是**干净的一张表**，没有复选框列。要清理时点卡片右上角的「**管理记录**」——此时每行左侧才出现复选框、表头出现全选，勾选若干行后右上角出现「删除所选 N 条」，再点「退出管理」收起（选择同时清空）。
2. 点行内「删除」或批量按钮，都会弹二次确认：标题按数量变化（「删除分析记录 #35？」/「删除这 2 条分析记录？」），提示写清「条目、逐条建议与补充记录一并删除，无法恢复；已保存的修改稿与历史版本不受影响」，主按钮是红色危险按钮。
3. 弹窗里的安全提示按选中内容变化：选中里有正在执行的任务 → 提示「等它结束后再删除」；否则若其中有已采纳的建议 → 提示「其中包含 N 条已采纳的建议——修改稿里的内容不会被回滚」。
4. 删分析的弹窗**没有**「先导出再删」（那是删简历专属的安全路径）。
5. 权限：批量接口按 `user_id` 过滤，别人的 id 只会出现在响应的 `missing` 里，一条都不会被删。

**实际结果**：见 `docs/test-results.md` 第 4.7 节（含一次真实的「建号 → 删除 → 后端 404」验证）。

### 场景十一：历史记录只读回放与报告导出

1. 在「历史记录」的表格里点岗位名或行内「查看」，进入 `/analyses/<id>`：这就是当初那次分析的结果页，但是**只读**的。
2. 顶部是这条记录的岗位、模型、时间与状态；下面是「这次分析的输入快照」——两个可折叠块分别是**发起分析时冻结的岗位描述**与**简历快照**。之后你改了简历或岗位，这里也不会跟着变，这正是「回到当时」的关键。
3. 结果区复用工作台的「要求—证据—判断」与「逐条修改建议」，但**不出现采纳/忽略/撤销，也不出现补充按钮**：采纳与补充写的是「当前修改稿」，从历史记录里操作会让人误以为改的是当时那一份，所以这里只给看。
4. 右上角「导出本次分析报告」下载一份 Markdown：记录信息、三态概览、当时的岗位描述、逐条「要求—证据—判断」与逐条建议（含当前处理状态）。报告只使用标题/加粗/列表这些本项目的 Markdown 渲染器认识的语法，粘回系统里也能正常显示。
5. 侧栏「历史记录」在回放页保持激活，返回列表点侧栏即可（不额外挂返回按钮）。

**实际结果**：见 `docs/test-results.md` 第 4.8 节（103 项浏览器断言全部通过，含回放页只读性、两份快照非空、导出反馈）。

### 场景十二：只读预览与「改素材」的边界（VER-07 的延伸）

1. 工作台的每张简历卡片底部是**「预览 / 编辑 / 打开并分析 / 删除」**，岗位卡片是**「编辑 / 删除」**。点「预览」弹出**只读**预览：`原始简历 / 修改稿` 两个页签，可切「放大字号」，里面**没有任何采纳、删除、保存按钮**——点开任何一份内容都不用先担心会不会改到东西。
2. 点「编辑」改素材：改**岗位**是名称 + 描述两个字段，弹窗里写明「已经跑过的分析保存的是发起时的岗位快照，历史记录与已有结果都不会跟着变」。
3. 改**简历**时，标题可以随便改（直接保存）；**正文一动，按钮就变成「保存（需确认覆盖）」**，点下去先出现一行红框确认块「将覆盖原稿正文（不可恢复）。已有的分析结果与历史快照不受影响。」＋「确认覆盖并保存 / 我再看看」。确认前一字节都不会写库。
4. 弹窗下方的「同时把**修改稿**重置为新原稿」**默认不勾**，文案会告诉你当前修改稿有多少字、与原文是否一致、不勾会怎样。已保存的版本一律不动。
5. 修改稿的版本历史每行右侧有一个**只读预览**的小眼睛（`v1 · 约 537 字 · 👁`），点开是 `v1（这一版）/ 当前工作稿` 两个页签，同样没有任何写操作。本轮**不提供「恢复这一版」**（见第 10 节已知限制）。

**实际结果**：见 `docs/test-results.md` 第 4.9 节（140 项浏览器断言全部通过；后端 96 个用例，其中 `tests/test_material_edit.py` 9 条专测素材编辑与快照冻结）。

## 7. 界面与视觉规范

2026-10-08 对前端做过两轮视觉重做。当前方向是**深色窄边栏 + 浅色工作区，颜色只留给语义**，不引入任何图片、图标库或外部字体（离线可用、纯原生 CSS），也没有新增前端依赖。

| 维度 | 规范 |
| --- | --- |
| 字体 | 系统栈 `-apple-system / Segoe UI Variable Text / PingFang SC / Microsoft YaHei / Noto Sans CJK SC`；数字与日期用 `tabular-nums` 对齐；等宽字体只用于模型名与账号。正文 14px / 行高 1.6，页面标题 20px，区块标题 14.5px，元信息 12.5px。 |
| 配色 | 边栏 `#1A1A1A`、工作区 `#F8FAFC`、卡片 `#FFFFFF`、文字 `#0F172A / #475569 / #64748B`。主色 `#3B5BDB` **只**用于导航激活态、链接与主操作，不铺大面积。三态：已体现 `#16A34A`、需要补充确认 `#D97706`、未体现 `#DC2626`；危险操作同样是 `#DC2626`。 |
| 按钮层级 | 三级：**主操作**＝主色实底白字（新建分析任务、保存简历/岗位、保存修改稿、采纳、登录、确认覆盖并保存）；**次操作**＝白底 + 主色边框（打开并分析、暂存草稿、导出 Markdown、忽略、重新分析、放大、管理记录）；**轻操作**＝无底色（删除、撤销、补充、查看、预览、编辑）。页内不再放「返回上一级」这类导航按钮——返回统一走左侧导览区（简历详情页在「工作台」下方有一个缩进的「← 返回工作台」子项）。 |
| 版式 | 间距刻度 4/8/12/16/24/32，圆角两档（卡片 10px、控件 6px），全部收敛成 `:root` 令牌；边栏固定 216px，内容区最大宽度 1120px。 |
| 视觉密度 | 工作台与历史记录用 2 列卡片网格（<1080px 自动单列）；分析区偏密，密度靠对齐与留白实现，不靠边框。 |
| 动效 | 卡片 hover 上浮 2px 并加深阴影（160ms）；**采纳一条建议后，修改稿里刚变的那一行淡入高亮 0.5s**；从原稿跳转的落点用主色底纹脉冲；原稿悬停按钮保留 200ms 淡出；`prefers-reduced-motion: reduce` 下一律降级（含取消上浮）。 |
| 可访问性 | 全局 `:focus-visible` 焦点环（边栏内用浅色环）；三态不只靠颜色，同时带文字标签与行左侧 3px 状态色条；窄屏（<900px）边栏变顶栏、全部单列，390px 无横向溢出。 |

九处结构性改动（功能与文案不变）：

1. **应用壳**：原来只放导航的顶栏收进左侧固定 `#1A1A1A` 边栏（品牌 / 工作台 / 历史记录 / 账号 / 退出登录），内容区独立滚动。导航激活态用主色实底。
2. **工作台改卡片网格，简历卡片顶部是匹配概览**：三段色条按**落库的三态计数**等比分配，下方图例给出「已体现 N / 需确认 N / 未体现 N / 共 N 条」，再下一行是「最近分析：岗位 · 时间 · 已采纳 N 条」。计数来自 `analysis_summary` 新增的只读字段 `status_counts` 与 `adopted_suggestion_count`（只做统计，不参与任何判定）。**这里刻意不做「匹配度百分比」**：需要补充确认既不是命中也不是未命中，压成单一分数会失真，也与「忠于输入材料」的定位冲突。一份简历跑过多次分析时，卡片只显示**最近一次成功**的分析，并标注岗位与时间。
3. **「要求—证据—判断」由 5 列表格改成行卡片**：一条要求一张行卡，左侧 3px 状态色条，卡顶是状态标记 + 序号 + 补充入口，卡内左右两栏是「岗位要求（原文）」与「简历对应原文」，下方是判断原因与「需要确认」追问。第 4 节仍是原稿/修改稿双栏对照：左栏只读原稿（悬停**只**浮出「编辑」；删除入口只在右栏修改稿），右栏修改稿用「预览 / 编辑」分段切换，暂存 / 保存 / 导出固定在右栏底部。未体现／需要补充确认的条目在卡片底部有主色的「＋ 补充这段经历」按钮（整张卡片只保留这一个补充入口，空证据格只写灰色的「（原文中无对应内容）」）；第 2 节标题右侧给出「待补充 N 条」。

4. **建议文本按 Markdown 渲染，原文保持逐字原样**：改写建议里的 `**加粗**` 与 `- 列表` 直接渲染成效果（旁边有「查看源码」可切回 Markdown 源码），避免用户对着 `**` 猜意思；「原文」块不渲染，保证「这就是原文」的可信度。岗位下拉右侧的绿色「匹配」徽标表示当前选中的岗位是**按简历标题预选**的那一个（原生 `select` 的 `option` 不能上色，所以标记放在下拉外侧），下拉项本身恢复干净文案。
5. **第 4 节只留对照，保存与版本独立成第 5 节**：原稿/修改稿双栏下方是一张横向卡片「5. 修改稿的保存与版本」——上排是「暂存草稿 / 保存修改稿（生成新版本）/ 导出 Markdown」动作条与保存状态（有未保存改动时转琥珀色），下排是版本历史；没有版本时不是一行灰字，而是琥珀色提示块「点上面的『保存修改稿』会在这里留下 v1」。
6. **工作台的「＋ 新建」按钮 + 弹窗**：新建简历/岗位由两个常驻长表单换成右上角一个主按钮，点开是带「简历（原稿）/ 目标岗位」页签的弹窗，保存成功后自动关闭并刷新卡片网格。

7. **返回入口移进侧栏，岗位下拉改成自定义列表**：简历详情页的「返回工作台」按钮从页头挪到左侧导览区（缩进在「工作台」下方，只在该子页面出现，父项保持激活）。岗位下拉从原生 `select` 换成自定义列表——原生 `option` 里放不下徽标、也没法可靠上色，而「哪个岗位是按简历标题预选的」需要一眼可见：现在**收起时按钮上就带绿色「匹配」**，展开后**预选岗位那一行右侧也有「匹配」**，并支持 ↑↓ 移动、Enter 选中、Esc 或点空白处收起。

8. **历史记录：一行操作 + 管理记录模式 + 只读回放页**：表格去掉常驻复选框列，改成右上角「管理记录」进入/退出，每行保留「查看 / 删除」。点「查看」或岗位名进入 `/analyses/<id>` 只读回放页（见场景十一）；回放页与工作台的「要求—证据—判断」「逐条修改建议」两节**共用同一个组件**，避免两处各写一遍之后慢慢长歪。

9. **一份只读预览弹窗 + 素材可编辑入口**：工作台卡片与简历详情页的版本历史接上同一个 `PreviewModal`——「放大」、简历「预览」、版本小眼睛三处入口共用「只读、可切页签、可放大字号、Esc 关闭」的一套行为，里面不出现任何写操作。素材不再只能新建：岗位卡片有「编辑」（`PUT /api/jobs/{id}`），简历卡片有「编辑」（`PUT /api/resumes/{id}`，可带 `reset_draft`）。改简历原稿要过二次确认；保存后的提示也按实际改了什么分开写——只改名称时提示「只改了名称，原稿与修改稿都没动」，不会让人误以为正文动了。

## 10. 已知限制

- 只处理纯文本简历，不支持上传 PDF/Word 解析，也不做 OCR、排版、投递、面试、排行榜等（与题目范围边界一致）。
- 不提供注册、验证码、找回密码与后台管理，账号由初始化脚本预置。
- 分析是**单进程后台任务**（FastAPI BackgroundTasks）。演示与验收场景足够；若要多副本部署，应换成独立队列并加分布式锁。
- 采纳建议采用“首次出现的原段落精确替换”。若用户先手动改写了同一段落，再次采纳会返回 409 并提示手动处理（这是有意为之，避免破坏用户的手工编辑）。
- **导出会写库**：为了让导出的就是最新修改稿，导出接口在发现工作稿有未保存改动时会先存出一个版本（备注「导出前自动保存」）。多次导出同一份未改动的工作稿只会在第一次生成版本，之后版本列表不再增加；但对“版本列表保持干净”有要求的用户，这条要提前知道。
- **删岗位不删分析**：历史分析继续可读，岗位名走分析时冻结的快照，所以即使岗位已被删掉，旧分析页面上仍显示当初的岗位名；如果你希望连分析一起清掉，需要先删简历（或另行实现）。
- 不提供匹配分数（题目说明中为可选项），重点放在依据、建议与流程完整性。
- **修改稿的版本只能看、不能「恢复这一版」**：版本历史每行右侧只提供只读预览（小眼睛），没有回溯恢复。想回到旧版本，需要自己把内容复制出来贴回修改稿。
- **改原稿不影响历史，也不一定影响下一次分析**：覆盖原稿只写 `resumes.original_text`，已有分析用的是发起时冻结的快照，不会跟着变；而新建分析读的是「修改稿优先」（`draft.content_md or original_text`），所以只改原稿却留着旧修改稿时，**下一次分析用的仍然是旧修改稿**。要么在编辑弹窗里勾上「同时把修改稿重置为新原稿」，要么把修改稿也一起改过来。
- 分析结果依赖模型输出，可能漏掉某些岗位要求；页面会提示“未返回可对应条目时请重试”，但不保证覆盖全部要求。
- 改写建议与“岗位要求”条目在界面上分区展示，没有做一对一外键关联：建议由模型在同一次分析中产出，可通过 `original_passage` 追溯到简历原文，但页面上不显示它是由哪一条要求引出的。
- **实体校验是启发式的，不保证 100% 覆盖**：四层规则（英文词元 / 中文技术词表 / 机构·系统后缀 / 中文数量词）能挡住常见编造，但中文技术词表之外的自造名词（例如“影子库”）不会命中，判断依据也只是“简历原文里出现过没有”。拿不准的内容仍需要你对着原文复核。
- **“无实质改动”的判定也是启发式的**：目前靠“归一化后逐字相等”（空白、大小写、“了／的”等助词、“有所／得到”等等价弱表达、“问题／情况”等空泛名词）来拦空建议，能挡住实测中出现的那几类换汤不换药，但不能覆盖所有同义替换；模型仍可能给出改动很小、价值不高的建议，用户可以点“忽略”。按当前边界，提示词已明确“不靠换词制造改动”，所以实际产出的建议以**拆句、列表化、加粗关键词**为主。
- `suggestion.action` 只在分析阶段用于决定是否允许携带改写文本，**不单独落库**：入库时映射为已有的 `is_question`（`补充` → 提问行），因此接口和数据库里没有 action 字段，也不需要新增迁移。
- **采纳补充后条目的 `match_status` 不会自动重判**：采纳只把内容写进修改稿，分析结论仍是这次任务的快照（界面上显示为“已补充”状态）。要看新内容带来的判断变化，需要**重新发起一次分析**——分析读的是**当前修改稿**，所以上一步补写的内容会被纳入下一次判断。
- **补充的事实边界以“用户这次的输入”为准，而不是简历原文**：这正是让用户自己提到的技术栈能被写进简历的原因；反过来，如果用户输入本身记错了，系统不会替他发现。润色稿与用户原文会在弹窗里并排展示，采纳前可以自己复核。
- **同一份材料重复分析，边界条目会有小幅摆动**：实测 `刘洋-Go后端简历 × 后端开发工程师（Go）` 在多次运行中给出过「已体现 5 / 需要补充确认 2 / 未体现 2」和「已体现 6 / 需要补充确认 2 / 未体现 1」两种分布（差别只在“参与系统性能优化与线上问题排查”这一条），`王强-口语化简历 × 后端开发工程师（初级）` 也出现过 2/2/2 与 1/2/3。不变量是：三类判断始终齐全、每条“已体现”都带原文逐字证据、不会出现简历里没有的内容。
- **「删除」入口只在修改稿栏**：原稿栏悬停只给「编辑」，完全没有删除按钮（原稿始终只读）；删除只是前端本地改动，改的是页面上的修改稿，需要点「暂存草稿」或「保存修改稿」才会落库，刷新页面会回到上次保存的状态（与直接在修改稿文本框里编辑的行为一致）。
- **删除是整行、且要求唯一定位**：按“去空白后严格相等”匹配，不做模糊或相似匹配。同一句话在修改稿里出现多次、是章节标题、或已被手改得对不上时，按钮会禁用并在提示里说明原因，需要到修改稿文本框里手动处理。
- **悬停交互在触屏设备上不可用**：没有 hover 就没有浮出按钮；触屏用户仍可用第 2/3 节的按钮与第 4 节右栏的「编辑」文本框完成同样的操作。

- **口语化表述本轮不自动改写**：`SYSTEM_PROMPT` 明确要求“口语词／非专业动词一律不换词”，只在追问里提示“建议改成更专业的书面表述”，由用户自己改。所以「王强-口语化简历」这类素材不会再产出改写建议——这是有意的取舍：换词最容易滑向“改写事实”，而这类句子往往同时缺指标，真正该做的动作是问清楚。
- **“参与／协助／配合”一律只提问**：出现这类看不出本人产出的词时，系统不替用户认定角色，也不会把“参与”升级成“负责／主导／独立负责”，只在追问里问清本人做了什么、产出是什么。
- **改写建议的粒度是整段**（同一小节下连续的 1〜3 行，含完整内容）：后端是把该段**原地替换**成建议文本（`draft.content_md = content.replace(original, suggested, 1)`），所以建议不跨段落、不跨小节、不截半句，也不会把相邻段落合并重写。
- **Markdown 排版是当前主要的改写形态**：加粗关键词、并列项列表化属于允许改动，纯排版改动也会被保留（`_squeeze` 只去空白，所以加 `**` 不会被“无实质改动”判定丢掉）；但排版只能落在该段覆盖的文字上，不会给整份简历加全局标题或分隔线。
- **删除分析记录不会回滚已经落到修改稿里的内容**：采纳只改工作稿，分析记录只是「当时的判断快照」。删掉分析后，修改稿与历史版本原样保留（`revisions.analysis_id` 置空），所以删除是安全的；反过来也意味着「删掉分析 ≠ 撤销采纳」，要撤销请用第 3 节的「撤销」。
- **`pending`（建了没跑）的任务可以删、也不挡删简历**：它不写任何数据，后台任务找不到记录会直接返回。这条是本轮修的一个死角——此前 `pending` 与 `running` 一起被算作「进行中」，一个从没跑过的任务会永久挡住删除。
